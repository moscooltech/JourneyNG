============================================================
0. AGENT INSTRUCTIONS
============================================================

You are the principal software engineer and technical lead responsible for implementing this application end-to-end.

Treat this document as the single source of truth unless a later explicit user instruction changes a requirement.

Do not merely generate a prototype, mock screens, or disconnected demo code. Build a coherent, runnable, testable application with a real backend, database, real-time location transport, authentication, consent enforcement, and Android background location support.

Core product principle:
"Share your journey, not just your location."

The application is a consent-based journey-sharing product. A host creates a journey to a destination and invites one or more visitors. Each visitor can join as a registered user or as a guest, explicitly consent to sharing their live location, start the journey, navigate to the destination, and stop sharing at any time. The host can monitor authorized active participants in real time.

Privacy is a product requirement, not an afterthought.

Do not implement:
- covert tracking
- persistent location tracking outside an active journey
- silent consent
- host-controlled tracking without participant consent
- indefinite GPS history by default
- sharing a participant's location with unauthorized users
- raw location coordinates in normal analytics or audit logs
- insecure invitation tokens stored in plaintext

When a requirement is ambiguous, choose the safest implementation that preserves the core user experience, document the assumption, and keep the implementation replaceable/configurable.

Before adding dependencies, check whether an existing dependency already solves the requirement. Keep the dependency set reasonably small.

The application must support:
- registered hosts
- registered visitors
- guest visitors
- multiple visitors per journey
- independent participant consent
- independent participant arrival/leave states
- live location
- background Android location through a foreground service
- navigation
- ETA/distance
- journey expiration
- automatic sharing termination
- host monitoring
- privacy controls

============================================================
1. PRODUCT DEFINITION
============================================================

Primary use case:

A person wants another person or group of people to come to a destination.

Example:
Babatunde creates a journey to his location.
He sends an invitation link to John, Sarah, and Mike.
John accepts and shares his location.
Sarah accepts and shares her location.
Mike declines.
Babatunde sees John and Sarah moving toward the destination in real time.
John arrives; John's sharing stops.
Sarah continues.
When Sarah arrives, her sharing stops.
The journey ends when the host ends it, it expires, or no active participant remains.

Positioning:
- "Share your journey, not just your location."
- "I'm coming to you."
- "The simplest way to safely share a journey."

Do not position the product as a permanent family surveillance/tracking application.

============================================================
9. JOURNEY STATE MACHINES
============================================================

Journey-level:

DRAFT -> INVITED
INVITED -> ACTIVE
INVITED -> CANCELLED
INVITED -> EXPIRED
ACTIVE -> COMPLETED
ACTIVE -> CANCELLED
ACTIVE -> EXPIRED

Do not allow:
COMPLETED -> ACTIVE
CANCELLED -> ACTIVE
EXPIRED -> ACTIVE

Participant-level:

INVITED -> ACCEPTED
INVITED -> DECLINED
INVITED -> EXPIRED
ACCEPTED -> ACTIVE
ACCEPTED -> LEFT
ACTIVE -> ARRIVED
ACTIVE -> LEFT
ACTIVE -> REMOVED
ACTIVE -> EXPIRED
ARRIVED -> no active sharing
DECLINED -> terminal
LEFT -> terminal
REMOVED -> terminal
EXPIRED -> terminal

Consent:
NOT_GRANTED -> GRANTED
GRANTED -> REVOKED
GRANTED -> EXPIRED

No active consent means no location access.

============================================================
10. JOURNEY END RULES
============================================================

Journey ends when:
1. host explicitly ends it, OR
2. journey expires, OR
3. there are no remaining active participants and product rules determine completion.

Recommended V1 behavior:
- If all participants are ARRIVED, DECLINED, LEFT, REMOVED, or EXPIRED, mark journey COMPLETED.
- If one participant arrives while others are active, journey remains ACTIVE.
- Host can end it at any time.
- Expiration terminates all active location sharing.

============================================================
13. LIVE LOCATION DESIGN
============================================================

Location is journey-scoped.

Do not maintain a permanent "user current location" feature in V1.

Preferred flow:

Android GPS
 -> native foreground service
 -> client-side validation
 -> HTTPS location endpoint
 -> FastAPI
 -> Redis live state
 -> WebSocket broadcast
 -> authorized host

Redis key examples:

journey:{journey_id}:participant:{participant_id}:location
journey:{journey_id}:participants
journey:{journey_id}:presence
journey:{journey_id}:connections

Redis entries must have TTLs.

Location freshness:
- LIVE: recent update within configured threshold
- STALE: no recent update but participant remains active
- OFFLINE/UNAVAILABLE: connectivity/location failure beyond threshold

The host UI must show "last updated" time.

Never freeze a marker and make it look live.

============================================================
14. LOCATION UPDATE OPTIMIZATION
============================================================

Initial configurable strategy:
- moving: approximately every 3–5 seconds
- normal movement: approximately every 5–8 seconds
- stationary/slow: approximately every 10–20 seconds

These are starting values, not immutable requirements.

Use movement-aware logic where possible.

Do not request routing recalculation on every GPS update.

Route recalculation triggers:
- journey starts
- meaningful route deviation
- destination changes
- provider requests reroute
- major navigation state change

Location upload rate must be configurable server-side.

27. AUTHORIZATION
============================================================

Authorization is server-side.

Rules:

Host can:
- view own journey
- invite participants
- revoke invitations
- view authorized participant locations
- remove participants
- end journey

Visitor can:
- view own journey
- accept/decline invitation
- grant/revoke own location consent
- start own journey
- send own location
- leave
- mark arrived

Visitor cannot:
- send another user's location
- view unauthorized participant location
- change another participant's consent
- extend their own authorization beyond server policy
- access another journey by guessing an ID

Backend derives identity from authenticated token/session.

Never trust client-supplied user_id for authorization.

32. LOCATION DATA VALIDATION
============================================================

Server validation:
- latitude between -90 and 90
- longitude between -180 and 180
- reasonable accuracy range
- reject malformed timestamps
- reject timestamps far in future
- reject extremely old updates based on configurable policy
- sequence/order handling
- optionally detect impossible movement speeds
- never discard legitimate GPS solely because it is imperfect

Do not use validation to infer wrongdoing.

- invitation creation per host
- join attempts per token/IP

- WebSocket connection attempts
- API requests per user/IP

Return HTTP 429 with retry guidance.

Do not hardcode limits into many modules.

- voice/calling
- additional map providers
- web host dashboard

Do not implement these now unless explicitly requested.

============================================================
64. FINAL PRODUCT PRINCIPLE
============================================================

The application is not a surveillance system.

It is a temporary, explicit, purpose-bound journey-sharing system.

Every technical decision should preserve these rules:

1. The participant knows sharing is active.
2. The participant knows who can see the location.
3. The participant knows why it is being shared.
4. The participant knows when sharing ends.
5. The participant can stop sharing.
6. The backend enforces these rules.
7. The application does not retain more location data than necessary.
8. The host sees current authorized journey information, not unrestricted personal location history.
9. When the journey ends, location sharing ends.
10. When consent ends, location access ends.

END OF SPECIFICATION
